## The crash cascade that masked the real signal — Cluster G (FIXED in this PR)

**One bug** in test code, two crash sites, ~453 cascade failures.

### Root cause

`URLSession` converts a request's `httpBody` to an `httpBodyStream`
before delivering the request to a `URLProtocol` subclass. So
`request.httpBody` is `nil` when read inside the stub's
`startLoading()`. Two tests force-unwrapped that nil with `!`,
which is a fatal `signal SIGTRAP` in Swift — not a Swift Testing
`Issue.record`. A trap inside the xctest worker takes down the
worker process, and **every other test currently running on
that worker** is reported as crashed. Swift Testing's default
parallel scheduler means tests from many unrelated suites were
in flight at the moment of the trap, so the cascade hit
~38 unrelated test classes.

Crash sites:

| File | Line | Force-unwrap |
|---|---:|---|
| `Civica Tests/InterviewCoachAPIClientTests.swift` | 154 | `req.httpBody!` |
| `Civica Tests/InterviewCoachAPIClientTests.swift` | 242 | `req.httpBody!` |

A third file (`EnrollmentAPIClientTests.swift:134`) had the same
latent bug but its `EnrollmentAuthTests`/`EnrollmentAPIClientTests`
suites were skipped at the suite gate, so the trap never fired in
this run. Fixed pre-emptively so it doesn't bite the next time
the gate opens.

A fourth file (`PracticeSessionViewModelTests.swift`) had a
compile error — `MockInterviewCoachClient` didn't conform to the
updated `InterviewCoachProviding` protocol after the
`fetchScore` method was added in commit `aaa1a1cd`
(`feat(practice-chatbot): close 3 gaps`). The test target
failed to compile at all, so the first xcodebuild run never
got to the test phase. **Also fixed in this PR.**

### Fix shipped in this PR

1. `Civica Tests/PracticeSessionViewModelTests.swift` —
   add `fetchScore` to `MockInterviewCoachClient` so the test
   target compiles.
2. `Civica Tests/InterviewCoachAPIClientTests.swift` and
   `Civica Tests/EnrollmentAPIClientTests.swift` —
   add a `capturedBodies: [Data]` static on each
   `URLProtocol` stub and a `readBody(_:)` helper that drains
   `httpBodyStream` into a `Data` if `httpBody` is nil. Replace
   the three `req.httpBody!` call sites with reads from
   `capturedBodies`.

This is the cleanest, most surgical fix:
- No production code changed.
- The body-stream pattern is the textbook iOS workaround for the
  URLSession/URLProtocol streaming behaviour, well known and
  documented in dozens of test frameworks.
- The stub still captures the full `URLRequest` (for header /
  method / URL assertions); only the body bytes needed a
  separate capture path.

### Cluster G impact

- 453 cascade "crashed" failures eliminated.
- 6 previously-passing `InterviewCoachAPIClientTests` cases
  continue to pass; 3 newly pass (the ones that crashed at
  `httpBody!`).

## The 4 remaining failures, in detail

### 1. `SNAPLocalEligibilityEvaluatorTests.maHouseholdOneOverThresholdIsIneligible` — Category C, **P0 candidate**

**File:** `Civica Tests/SNAPLocalEligibilityEvaluatorTests.swift:45`
**Symptom:** `result.status` is `.eligible` when the test expects `.ineligible`.
**Setup:** MA household of 2, gross monthly income $3,409,
not a student, evaluated against FY26.

**Why this matters.** MA BBCE threshold for 2-person household at
200% FPL is ~$3,408–$3,409 depending on rounding. If the test
fixture is `3_409` and the evaluator now returns `.eligible`,
either:
- the BBCE threshold table was bumped up (FY26 COLA?), making
  `3_409` legitimately under-threshold, OR
- the evaluator's comparison flipped from `>` to `>=`, OR
- the FPL multiplier rounding changed.

This is the **single highest-value finding from this triage** —
it's a substantive eligibility-determination behaviour
difference. Either the test fixture needs updating to a value
that's truly over the new threshold (e.g. `3_500`), OR the
evaluator has regressed and is now telling MA users they're
eligible when they aren't.

**Recommended next step.** Look up the FY26 MA BBCE 200%-FPL
threshold for household size 2 (probably in
`Civica/Features/SNAP/Rules/MAStateRules.swift` or in
`packages/snap-rules/data/`) and compare to `3_409`. If the
threshold is now `> 3_409`, this is a stale-fixture (Category
B) and the fixture should be updated to e.g. `3_500`. If the
threshold is `<= 3_409`, this is a real eligibility
regression and warrants a focused investigation PR.

**Severity:** P0 if regression, P3 if stale fixture. Cannot
determine without checking the threshold table.

### 2. `MAStateRulesTests.minimumBenefitDelegatesToFederal` — Category B, P3

**File:** `Civica Tests/MAStateRulesTests.swift:91-93`
**Symptom:** `rules.minimumBenefit(asOf: fy26Date)` returns `24`; test expects `23`.

`Civica/Features/SNAP/Rules/FederalDefaultRules.swift:367` has:

```swift
static let minimumBenefitSnapshots: [PolicySnapshot<Decimal>] = [

```

FY26 federal minimum SNAP benefit is in fact $24 (USDA COLA
memo, 2025-08). The test hardcodes `23`, which is the FY25

**Fix recipe** (one-line):

```swift

+ #expect(rules.minimumBenefit(asOf: fy26Date) == 24)
```

Also check `CAStateRulesTests.swift:83` (same test name exists
there) — that one currently passes, which means either it's
already on `24`, or `CAStateRules` doesn't delegate the same
way. Worth a sanity look.

### 3. `SNAPComplianceCopyTests.noSNAPSwiftFileContainsRegistryBannedPhrase` — Category C / test bug, trivial

**File:** `Civica Tests/SNAPComplianceCopyTests.swift:320-346`
**Symptom:** The test scans every Swift file under
`Civica/Features/SNAP/` for any registry banned phrase and
asserts none contains one. Current exclusion list is exactly
one file: `SNAPComplianceCopyRegistry.swift`. The test is now
flagging `SNAPComplianceCopyRegistry+Generated.swift` — a
sibling generated file that *also* contains the banned phrases
as data (it's the codegen output of the
`@civica/snap-compliance-copy` package per recent project memory).

The exclusion check on line 328-333 was written against a
single hand-authored registry file, before the codegen sibling
existed.

**Fix recipe** (one-line):

```swift
// SNAPComplianceCopyTests.swift:328
- let excludedFile = "SNAPComplianceCopyRegistry.swift"
+ let excludedPrefixes = ["SNAPComplianceCopyRegistry"]
  // ...
- for case let url as URL in enumerator where url.pathExtension == "swift"
-     && url.lastPathComponent != excludedFile {
+ for case let url as URL in enumerator where url.pathExtension == "swift"
+     && !excludedPrefixes.contains(where: { url.lastPathComponent.hasPrefix($0) }) {
```

I did not bundle this fix into this PR because it touches the
compliance-copy registry parity contract, which has a
documented review process. The fix is mechanical but the
reviewer should confirm it's the right exclusion scope.

**Severity:** P2 — test logic bug, no production code at risk.

### 4. `SNAPComplianceCopyTests.recertSMSDropsRECERTKeyword` — Category C / test logic bug, P2

**File:** `Civica Tests/SNAPComplianceCopyTests.swift:476-486`
**Symptom:** assertion fails because `approvedEnglish` contains
the substring "RECERT" (inside "recertification" / "recertify").

Test code (lines 480-481):

```swift
#expect(row?.approvedEnglish?.uppercased().contains("RECERT") == false ||
        row?.approvedEnglish?.uppercased().contains(" RECERT") == false)
```

The intent (per the doc comment on line 474: *"the RECERT
keyword phrase must be removed from the recert SMS copy"*) is
to check the **standalone uppercase keyword** "RECERT" — the
SMS reply keyword — is not in the message, while it's fine
for the word "recertification" to appear in normal sentence
case.

The two `contains` checks both look for case-insensitive
"RECERT" / " RECERT" via `.uppercased()`, which will always
match "recertification" anyway. The `||` makes it strictly
weaker, but neither side actually targets the SMS keyword.

Also, the state-loop on lines 482-485 already uses
`.contains(" RECERT ")` (with word-boundary spaces) without
the `.uppercased()` call. That's the right comparator and
should be lifted to the flat-default check too:

**Fix recipe:**

```swift
// SNAPComplianceCopyTests.swift:480-481
- #expect(row?.approvedEnglish?.uppercased().contains("RECERT") == false ||
-         row?.approvedEnglish?.uppercased().contains(" RECERT") == false)
+ #expect(row?.approvedEnglish?.contains(" RECERT ") == false,
+         "Flat-default copy still mentions the RECERT SMS keyword")
```

Not bundled into this PR for the same reason as #3 — touches
the same compliance-copy contract.

**Severity:** P2 — test logic bug; production copy is already
clean of the SMS keyword (per the same registry that the test
is inspecting).

## Anything weird that surfaced

1. **`Test Suite 'All tests' passed at ... Executed 0 tests`**
   lines appear repeatedly in the raw log when the test
   process crashes and Swift Testing re-runs the surviving
   tests. These are bookkeeping artifacts of the cascade,
   not real test events.

2. **Swift Testing parallelism vs `.serialized` suites.** The
   `.serialized` modifier serializes tests *within* a suite,
   but Swift Testing still parallelizes *across* suites by
   default. A single trap in one suite therefore takes out
   tests in many unrelated suites. Worth knowing — if a
   single bad test starts crashing again, the failure picture
   will look like a project-wide meltdown rather than what it
   actually is.

3. **Real test count is 500, not 445.** Tests have grown
   since the last reliable baseline was captured. The 148/445
   number in `project_uat_dashboard_may2026.md` and
   `feedback_ios_ci_patterns.md` is now stale; the new number
   to remember is **464 / 4 / 32 (passing / failing / skipped)
   out of 500**, achieved on `chore/ios-test-triage-2026-05-20`.
