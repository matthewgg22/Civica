## Problem Statement

Civica's repositioning as SaaS-to-CBOs ("the caseworker before the caseworker") rests on a capability that does not yet exist: a **row-level shadow caseworker** that simulates the determination a CalSAWS-trained county worker will make on an application packet, BEFORE submission. The existing `scoreErrorRisk()` engine in `packages/snap-qc-engine` predicts packet-level error probability (a single risk tier) — it does NOT produce row-level narrative determinations matching what a real worker would write.

Without this capability, the "essentially guaranteed approval if it passes our dry-run" claim is marketing, not engineering. With this capability, Civica has a defensible process guarantee, a CBO-licensable artifact, and the foundation for B2G error-rate contracts in 2027.

## Demand Evidence

- **Existing infra demands it.** `packages/snap-rules` (JSON DSL for eligibility) + `packages/snap-qc-engine` (risk scorer + USDA citations) are shipped. A row-level worker-simulation layer is the missing piece between them.
- **CEO review locked positioning.** "Same submission destination, less uncertainty." 30-day approval anxiety collapsed to "confirmed approved at submission." Requires dry-run that meets >95% prediction confidence on procedural denials.
- **Path-1 generates training data.** Civica-as-CBO submissions in CY2026-2027 generate per-applicant outcome data. Dry-run engine ingests + calibrates against actual worker outcomes over time.
- **PRA returns sized.** CDSS Filing #2 (per-county PER + denial codes, due July-Aug 2026) + CalSAWS Consortium PRA fills 30-50% of the row-level reject-code library; Civica-as-CBO ops fills the rest organically over 6-12mo.

## Status Quo

- `scoreErrorRisk()` v0.2.0 emits packet-level risk tier (low/med/high) with USDA citation row-by-row in `error-risk.ts` comments.
- `snap-rules` evaluates eligibility checklist (BBCE, SB 1090, HCSUA, ABAWD age-band) via JSON DSL.
- `snap-qc-engine` has tier-aware THESIS_CALIBRATION_FACTOR ≈ 0.912 for engagement-implied PER projection.
- iOS `RecertificationCompanion` has a "Phantom Recert" 60-day dry-run — distinct concept (renewal interview simulation), but reusable UX scaffolding.
- No engine today produces "row N: verification status = MISSING; expected denial reason = NOMI-PaystubInsufficient; cure window 10 days; confidence 0.92."

## Target User & Wedge

**Primary user (internal):** Civica navigator submitting packets via Civica-as-CBO Path 1 — wants pre-submission confidence + cure asks before clicking submit.

**Primary user (SaaS):** Mid-size multi-program CBO ED's navigator team — wants the same engine licensed as a packet-quality gate that runs on packets prepared via GetCalFresh + Civica overlay.

**Wedge:** the dry-run output is the artifact that produces (1) applicant confidence ("you're approved"), (2) navigator confidence ("nothing to cure"), (3) ED-level confidence ("our org's packets clear at 96%+").

## Constraints

- **Defensibility non-negotiable.** Every row-level output must trace to either a deterministic rule (with CFR/ACL citation) or an LLM-assisted judgment (with eval-suite calibration + navigator-routing escape hatch). No silent unverifiable outputs.
- **Privacy.** LLM layer prefers on-device Apple Intelligence Foundation Models for applicant PII paths; Claude API server-side acceptable for non-PII reasoning (e.g., rule disambiguation against CDSS ACL corpus).
- **Determinism on the bedrock.** Structured cases (verification present/absent, math correct, BBCE asset rule applied) MUST be deterministic — no LLM in the path for facts that are facts.
- **Ambiguity routing.** When the engine is < confidence threshold, route to navigator review. Engine never silently guesses.
- **Extend, don't fork.** Builds inside `packages/snap-rules` + `packages/snap-qc-engine`. No new top-level package.
- **Engine ships v1 BEFORE CBO sales begin.** Sequencing per CEO plan: Path-1 dogfood → measured cohort → SaaS sales.

## Agreed Premises (from Phase 3)

1. The dry-run can predict worker determination accurately enough that "passing it" yields >95% approval at formal review, IF PRA-derived reject-code library + CDSS rule chains are in place.
2. The dry-run is the load-bearing SaaS claim ("caseworker before the caseworker"). Without it, Civica is GetCalFresh + dashboard.
3. Implementation extends `packages/snap-rules` (JSON DSL) + `packages/snap-qc-engine`. Not a new package, not a rewrite.
4. PRA returns + Civica-as-CBO ops data jointly fill the reject-code library over 6-12 months.
5. Ambiguous worker discretion cases route to navigator review. Engine doesn't pretend to know.
6. Ship sequence: dry-run v1 (hybrid core) ships BEFORE CBO sales begin.

## Cure-ask workflow

When tree evaluator emits FAIL on a row, engine generates a structured cure-ask:

```
{
  element: "shelter-deduction",
  status: "FAIL",
  reason: "Lease document uploaded but OCR confidence < 0.75 on monthly rent line",
  cure_action: {
    type: "RE_UPLOAD",
    description: "Take a clearer photo of the rent line on your lease",
    estimated_minutes: 2,
    blocks_submission: false,
    expected_resolution: "OCR confidence ≥ 0.90 OR navigator confirms manually"
  },
  citation: "7 CFR 273.9(d)(6)(ii)"
}
```

Cure-asks are surfaced in iOS app + navigator dashboard. Submission gate: applicant can choose to submit anyway (with FAIL flagged) OR cure first. Default UX: cure first.

## Ambiguity routing

Tree evaluator emits one of: `PASS`, `FAIL`, `AMBIGUOUS`. AMBIGUOUS triggers the LLM layer with strict guardrails:

```
LLM input:
  - tree path that led to AMBIGUOUS
  - relevant packet rows
  - CDSS ACL citations (retrieved from packages/snap-qc-engine/citations)
  - confidence threshold (configurable, default 0.85)

LLM output (structured):
  - resolution: "PASS" | "FAIL" | "ROUTE_TO_NAVIGATOR"
  - confidence: 0.0-1.0
  - reasoning: 1-2 sentences (worker-voice)
  - citation: ACL/CFR ref

If LLM confidence < threshold: force ROUTE_TO_NAVIGATOR regardless of resolution.
If LLM outputs ROUTE_TO_NAVIGATOR: surface to navigator dashboard queue.
```

## Eval suite

The LLM layer requires a golden fixture set + eval suite. Each fixture:

```
fixtures/
  ambiguous-sublease-tenancy.json     # packet
  ambiguous-sublease-tenancy.expected # expected resolution + reasoning shape
  ambiguous-medical-deduction.json
  ambiguous-medical-deduction.expected
  ... (target: 50+ fixtures spanning all AMBIGUOUS tree exits)
```

Eval suite runs on every PR touching the LLM layer. Threshold: >= 90% match on resolution direction, >= 80% on citation correctness, narrative quality scored by a separate LLM-as-judge prompt (target >= 4/5 mean score).

## Open Questions

1. **Tree authoring tooling.** Who authors the JSON trees in practice? SMEs (CDSS-trained navigators) need a UI, OR engineering authors initially and SMEs review. v1: engineering authors with SME review. v1.5: SME-editable web UI.
2. **LLM provider for ambiguity layer.** Claude API server-side (capability, eval-rich) vs Apple Intelligence on-device (privacy, no API cost). Likely default to Claude API for ambiguity (server-side, non-PII rule reasoning) + Apple Intelligence remains for OCR + applicant-facing PII paths.
3. **Confidence threshold tuning.** What's the calibration target for "PASS implies >95% approval"? Set initial threshold conservatively at 0.85 LLM-layer + 1.0 tree-layer (pass only on full deterministic confidence); calibrate down as Civica-as-CBO data accumulates.
4. **What's the right name?** "Dry-run" already means Phantom Recert in this codebase. Candidates: `WorkerSimulation`, `DeterminationPreview`, `ShadowDetermination`, `PreSubmissionValidator`. **Recommendation: `WorkerSimulation` for the engine package + `DeterminationPreview` for the user-facing artifact** (mirrors what the applicant/navigator sees).
5. **OBBBA Track 1.3 + Q5 distress gate `pending_counsel` status.** How does the dry-run handle elements whose rules aren't yet counsel-approved? v1: emit `PENDING_COUNSEL` as a distinct status, surface to navigator dashboard for manual review.
6. **Eval suite baseline.** What's the source-of-truth for "expected resolution"? Goldens authored by engineering + SME-reviewed initially; once Civica-as-CBO ops generate outcome data, calibrate against measured outcomes.

## Risks

| # | Risk | Mitigation |
|---|---|---|
| 1 | Tree library too thin at v1 launch — many AMBIGUOUS exits | Calibrate threshold higher initially; route more to navigator. Trees grow w/ PRA returns. |
| 2 | LLM eval drift on Claude API model updates | Pin model version; eval suite gates deploys; track eval scores over time |
| 3 | Prompt injection via applicant-controlled fields (name, address) | LLM never reads PII strings; only structured tree-path data + ACL citations |
| 4 | Defensibility challenged in regulatory audit | Every PASS row traceable to deterministic rule + citation; AMBIGUOUS rows logged with reasoning + confidence; navigator can override |
| 5 | "Phantom Recert" name collision causes user confusion | Rename application-time engine to `WorkerSimulation` + `DeterminationPreview` UX surface |
| 6 | OBBBA `pending_counsel` items have no rule | Distinct `PENDING_COUNSEL` status; engine surfaces but doesn't decide |
| 7 | First 10 CBO customers experience FAIL rate > expected because trees too strict | Pre-launch calibration cohort (Civica-as-CBO Path 1) tunes thresholds |

### IA — Screen anatomy (top → bottom)

├─────────────────────────────────────────┤
│ 3. ASYNC STRIP  (ANALYZING only)        │  warning surface, dismisses on resolve

├─────────────────────────────────────────┤
│ 4. VERIFICATION SECTION                 │  compact list, pine checkmarks
│    "Already verified"                   │  hairline-divided rows (no card chrome)

### 9-state coverage matrix

| State | When | Verdict strip | Action section | Verify section | Footer CTA | Surface |
|---|---|---|---|---|---|---|
| **EMPTY** | First time, no run yet | "Check before you submit" + 3 educational bullets | hidden | hidden | "Run the check" (pine) | paper |
| **LOADING** | Trees still evaluating (<200ms) | "Checking..." + spinner | hidden | hidden | disabled gray | paper |
| **ANALYZING** | Trees done, LLM pending | "Almost done — confirming one detail" | hidden | shown (already verified rows) | disabled gray | paper + warning strip top |
| **PASS** | All rows verified | "Ready to submit" pine pill | hidden | shown | "Submit application" (pine) | paper + amber benefit tile |
| **MIXED** | Some FAIL with cures | "N things to fix before submitting" | shown (brick cards) | shown below | "Fix items above" (pine) | paper |
| **REVIEW** | Engine routed to navigator | "A specialist will review your application" | shown (warning explanation cards) | shown below | "Send to navigator" (pine) | paper |
| **FAIL** | All cures, no path forward | "Major changes needed" | shown (brick cards) | shown below | "Talk to a navigator" (pine) | paper |
| **ERROR** | Engine error / network | "Couldn't check right now" + reason | hidden | hidden | "Try again" (pine) + "Submit anyway" Footnote | paper |
| **PARTIAL** | Offline cached run, some stale | "Last checked X ago" stale chip + amber notice | shown if any FAIL | shown | "Re-check" (pine) | paper |

### Semantic palette (locked — write this into `DryRunPanel.swift` header comment)

```
SEMANTIC PALETTE RULES for DryRunPanel:
- pine     → "verified / ready / approved" outcomes
- brick    → "needs cure / recovery / action required"
- amber    → POSITIVE OUTCOME ONLY (benefit award estimate tile). NEVER for warnings.
- warning  → PROCESS state (async pending, pending-counsel rows)

DO NOT use amber for cure-asks even if it "looks softer." brick is correct
because the user must act. amber misuse is the most common color drift bug
in this codebase (see DESIGN.md §2.2).
```

### Async LLM landing UX (Q1 locked)

- **Default:** 200ms fade+slide replacement of the ANALYZING strip with the resolved row (verified pine row OR cure brick card depending on resolution).
- **Reduce-motion:** instant content swap, no animation. Gates on `UIAccessibility.isReduceMotionEnabled`.
- **VoiceOver:** polite live-region announcement on resolve: "Reviewing [element]" → "Verified [element]" or "Needs attention: [element]".
- **Timeout:** if LLM doesn't return within 30s, fall back to `REVIEW` state (route to navigator). This closes the critical gap from the eng review.

### Cure-ask interaction model (Q2 locked)

```
Applicant taps CTA on brick FAIL card
  → deep-link via SNAPApplicationFlowOrchestrator to the relevant intake step
    (lease photo step, paystub upload, household composition, etc.)
  → applicant resolves the input
  → orchestrator returns to DryRunPanel
  → auto-re-run dry-run on return
  → updated DryRunReport renders (the just-cured row should now be in
    Verification section, ideally with a subtle "Just fixed" pine chip
    for 3 seconds before settling into the standard verified row treatment)
```

No modal sheets. No in-place capture. The intake flow is the single source of truth for any step that can produce a cure.

### Submit-anyway override (Q3 locked)

```
Trigger: applicant taps "Submit anyway" Footnote-link in MIXED state footer
Render: confirmation dialog (native SwiftUI .confirmationDialog)
  Title: "Submit with N issues unresolved?"
  Body (list): bullet per unresolved cure ("Lease photo unclear",
                "Pay stub needs more recent date")
  Body (footer): "Submitting now will likely trigger a 10-day cure notice
                 from the county worker, delaying your approval."
  Actions:
    [Go back and fix]  (pine fill, primary)
    [Submit anyway]    (brick text, destructive role)
    [Cancel]           (default, dismisses)
Logging: any override fires an audit event with the unresolved rows + reason
         (logged for navigator-side review queue + eng-review-driven analytics).
```

### Cure-resolved transitions (Q5 locked)

Animation philosophy: brief satisfaction beat, no forced tap, momentum preserved.

**Partial cure (1 of N resolved, ≥1 brick card still open):**

```
T+0ms     Cured row shows a pine "Just fixed" chip overlaying its brick-card
          position. Card content stays visible underneath the chip; chip is
          ~24pt tall, pineSurface background, pine text. Border-radius matches
          the card (12px).

T+1500ms  Card begins 200ms fade-out from action section position.
          Simultaneously, the row fades in (200ms) in the verified section
          at its natural sort position (element order).

T+1700ms  Transition complete. Verdict strip text has cross-faded to reflect
          new count ("2 things to fix" → "1 thing to fix"). Footer CTA label
          unchanged ("Fix items above"). Action section header stays visible
          because ≥1 brick card remains.
```

**Full cure (all cures resolved — MIXED → PASS):**

```
T+0ms      All remaining cure rows show pine "Just fixed" chip simultaneously.

T+1500ms   Full-screen fade-cross transition begins (300ms total).
           - Cured rows fade out from action section position.
           - New PASS screen content fades in:
             • Verdict strip text crossfades "N things to fix" → "Ready to submit"
             • Verdict strip color crossfades from ink → pine
             • Action section header + brick cards fade out completely
             • All rows now appear in verified section (V1 ledger layout)
             • Benefit estimate amber tile fades in (was hidden in MIXED)
             • Footer CTA crossfades from "Fix items above" → "Submit application"

T+1800ms   Transition complete. Screen is in PASS state (A-ready). Applicant
           can submit immediately. No required tap, no intermediate confirmation.
```

**Reduce-motion fallback (`UIAccessibility.isReduceMotionEnabled == true`):**

```
- Pine "Just fixed" chip still appears for 1.5s (semantic acknowledgment,
  not motion). The chip itself does not animate.
- All fade-cross transitions become INSTANT state swaps. No fading, no
  sliding, no cross-fade.
- Rows just appear in their new positions at T+1500ms.
```

**VoiceOver announcements (polite live region):**

```
Partial cure:  "[Element label]. Just fixed. Now verified."
                Then: "[N-1] item[s] still need attention."

Full cure:     "All items resolved. Application ready to submit.
                Expected benefit: [$X] per month."
```

**Edge case — re-fail after PASS:**

If the applicant edits intake after PASS and a row re-fails on next dry-run, the screen transitions PASS → MIXED. Same animation philosophy in reverse:

```
- Re-failed row gets a brick "Needs another look" chip for 1.5s in its
  verified-section position.
- 200ms fade-out from verified section, 200ms fade-in to action section.
- Verdict strip updates: "Ready to submit" → "1 thing to fix"
- Benefit estimate amber tile fades out.
- Footer CTA: "Submit application" → "Fix items above"
- Reduce-motion: same as above, instant.
```

**Implementation notes:**
- Use SwiftUI `.transition(.opacity)` + `.animation(.easeInOut(duration: 0.2))` gated on `reduceMotion`.
- The pine "Just fixed" chip uses `CivicaColors.pineSurface` background + `CivicaColors.pine` text + `Typography.bodyStrong`.
- The 1.5s acknowledgment delay must run on the main actor; do NOT defer it to a background queue.
- VoiceOver announcements use `AccessibilityNotification.Announcement(...)` with polite priority.

Verdict strip:

### Anti-AI-slop guards (locked into spec — implementer reference)

- NO 3-column grids anywhere on DryRunPanel. Vertical lists only.
- NO purple/violet/indigo. Palette is brick/pine/amber/warning + paper/ink/graphite ONLY.
- NO decorative blobs, no floating particles, no wavy SVG dividers.
- NO emoji as design elements. SF Symbols only (with VoiceOver labels).
- NO hero copy. NO "Welcome to your dry-run." NO "Unlock your benefits."
- Cards appear ONLY in the action section (FAIL/cure rows). Verification rows are hairline-divided plain rows, NEVER card-wrapped.
- Benefit estimate gets `amberSurface`. Nothing else on this panel gets amber.
- Mirror `PhantomRecertSummaryView`'s vertical three-section pattern. Distinguish via copy + state, not via visual novelty.
