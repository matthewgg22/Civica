## 1. Purpose and Scope

This policy governs the collection, storage, access, and deletion of data generated by or passed through large-language-model (LLM) API calls within the Civica SNAP eligibility screener ("the Product"). It applies to:

- All LLM inference calls made by the `civica-snap-engine` service (voice extraction, document quality check)
- All LLM-adjacent data flows through `civica-enrollment-api` Edge Functions
- All observability tooling (Sentry error events, log drains) that may receive data from the above

This policy does **not** govern the local, deterministic rule engine (`SNAPRuleEngine`) — no LLM call occurs in that path.

---

## 2. Core Retention Rules

| Data category | Primary TTL | Backup TTL | Total max retention |
|---|---|---|---|
| LLM input / output logs (structured, de-identified) | 90 days from last user interaction | 30 days after primary expiry | 120 days |
| Raw voice transcripts | **0 days — must not be stored** | N/A | 0 days |
| Document image content | **0 days — must not be stored** | N/A | 0 days |
| Eligibility estimates (structured JSON, no PII) | 90 days | 30 days | 120 days |
| Enrollment routing decisions | 90 days | 30 days | 120 days |

**"Last user interaction"** = the most recent timestamp at which the user's session record was read or written. Not the creation date.

**Raw voice transcripts and raw document content must never be stored.** Only the structured output of LLM processing (intent classification result, quality score) may be retained.

> ⚠️ **Conflict note:** `docs/snap/retention_policy.md` specifies 7-year retention for document image blobs in Supabase Storage (row: "Document image blobs in Storage"). If that policy reflects a product decision to retain the uploaded document for the user's benefit (e.g., re-review), counsel must decide whether the LLM-processed content (the document as passed to the LLM) must be destroyed immediately even if the original file is retained separately. The positions are not necessarily incompatible but must be explicitly harmonized.

## 3. PII Handling

### 3.1 What may be stored

- Household size (integer)
- Income band (not raw dollar value — e.g., "130–200% FPL", not "$2,400/month")
- State code
- Categorical eligibility flags (boolean)
- Eligibility result enum
- Routing decision enum

### 3.2 What must never be stored

- Full name
- Social Security Number or any fragment thereof
- Date of birth
- Raw dollar income values
- Street address
- Any voice transcript text
- Any document text extracted from uploaded documents
- Immigration status beyond a boolean citizenship flag

### 3.3 Sentry / Observability PII scrubbing

All PII must be scrubbed from Sentry events **before events leave the device or service**, using:

- **`beforeSend` hook** — scrubs event payload fields before transmission
- **`beforeBreadcrumb` hook** — scrubs breadcrumb content; this is a **separate hook** from `beforeSend` and must be configured independently to prevent transcript fragments from appearing in Sentry breadcrumbs

Fields that must be scrubbed from both hooks:

```
name, ssn, ssn_last4, dob, income, gross_income, net_income,
address, street, zip, voice_transcript, document_text, case_id
```

A signed Sentry DPA does not substitute for scrubbing. A DPA governs the contractual relationship; the `beforeSend` / `beforeBreadcrumb` scrubbers govern the technical behavior. Both are required.

## 4. Access Control (RBAC)

| Role | Access |
|---|---|
| `user` | Read own data only (Supabase RLS: `user_id = auth.uid()`) |
| `admin` | Read-only audit access to retention data; writes prohibited via UI |
| `engineer` | No direct-DB access to PII tables in production; must use admin UI or audit function |

All admin-role access to retention data must be logged with: timestamp, actor ID, table accessed, query type. Log destination: Supabase audit table (separate from PII tables).

---

## 5. Third-Party LLM Provider Zero Data Retention (ZDR)

All LLM API calls that process PII (voice extraction, document quality check) **must use a provider with Zero Data Retention (ZDR) configured**:

- **OpenAI:** Enable ZDR at `platform.openai.com → Settings → Data Usage & Privacy → API Data Usage`. Confirm ZDR is active before beta.
- **Other providers:** Confirm equivalent data retention = 0 in writing before use with PII.

ZDR means the provider does not retain prompts or completions for model training. A signed Data Processing Addendum (DPA) is also required — the DPA governs the contractual relationship; ZDR governs the technical behavior. Both are required.

## 6. User Rights

### 6.1 Right to Deletion (CCPA)

Users may request deletion of their data at any time. Handled manually for v1.

**SLA:** Deletion completed within **45 days** of verified request. This is the CCPA-required maximum — do not extend it.

**Scope:** All PII fields in `snap_enrollments`, `snap_estimates`, `snap_intake_events`, `snap_doc_checks` for the requesting user. Backup copies deleted within 30 days of primary deletion.

See also `docs/snap/retention_policy.md` for the SQL deletion runbook (subject-initiated deletion procedure).

### 6.2 Right to Know (CCPA)

Users may request a description of the data Civica holds about them. Handled manually via email for v1. Provide within **45 days**.

## 8. Incident Response

In the event of a data breach involving PII:

1. Assess scope within **24 hours**
2. Notify counsel within **24 hours**
3. CCPA notification to affected users required within **72 hours** of discovery
4. Sentry alert must be wired to a monitored channel (Slack, email) before beta

A documented incident response runbook must exist before beta launch. See [`docs/snap/incident_response.md`](incident_response.md).
